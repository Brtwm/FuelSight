# FuelSight ML and Pipeline Design

## Цели ML-контура
- Прогноз спроса по каждому виду топлива на горизонтах `1`, `7` и `30` дней.
- Дать пользователю объяснимый результат: прогноз, доверительный интервал, метрики качества и драйверы.
- Сохранить воспроизводимость даже без реальных данных за счёт учебного генератора.

## Базовый ML-стек
- Основная модель: `CatBoostRegressor`
- Бейзлайн: `Seasonal Naive`
- Допустимые расширения: `LightGBM`, `XGBoost`, `SARIMA` как исследовательские альтернативы
- Метрики: `MAE`, `RMSE`, `SMAPE`
- Схемы проверки: `rolling window`, `expanding window`

## Признаки
- лаги спроса: `t-1`, `t-7`, `t-14`, `t-28`
- скользящие статистики: mean, median, std за окна `7/14/28`
- календарные признаки:
  - день недели;
  - номер месяца;
  - признак выходного;
  - признак праздника РФ;
  - сезонный период `summer/winter`
- ценовые признаки:
  - `avg_retail_price_rub`
  - `purchase_price_rub`
  - `gross_margin_rub_per_liter`
  - относительное изменение цены
- внешние признаки:
  - курсовые и биржевые индикаторы при наличии;
  - индикаторы из Росстата / MOEX / EIA как дополнительный контекст.

## Принцип хранения признаков
В `v1` отдельная таблица `features_daily` не обязательна. Признаки могут формироваться внутри пайплайна и сохраняться как parquet-артефакты в файловой системе для backtest и обучения. Если в проекте позже появится необходимость повторного использования витрины несколькими сервисами, допускается перенос feature store в PostgreSQL.

## Генератор учебных данных
- Вход: период, набор продуктов, random seed.
- Что моделируется:
  - базовый уровень спроса по каждому продукту;
  - недельная сезонность;
  - летний и зимний сезон;
  - эластичность спроса к изменению цены;
  - редкие промо-эффекты;
  - шоки закупки и последующая реакция розничной цены.
- Выход: согласованные таблицы `sales_daily` и `purchases_daily`.

## On-demand прогноз
1. Backend получает запрос на прогноз от `/api/v1/forecasts/run`.
2. Выбирается активная модель по продукту и горизонту.
3. Если модель отсутствует, используется fallback baseline и возвращается `model_status=baseline_fallback`.
4. Если передан scenario, ценовые признаки корректируются только на запрошенный горизонт.
5. Результат сохраняется в `forecasts` и возвращается в API вместе с драйверами.

## Объяснимость
- Для интерфейса не использовать “сырые” SHAP-графики как основной output.
- Основной пользовательский слой:
  - топ-драйверы за период;
  - краткое текстовое пояснение;
  - what-if эффект изменения цены;
  - предупреждение, что сценарный эффект — модельная оценка, а не обещание результата.
- SHAP допускается как внутренний технический слой или приложение к диплому.

## Airflow DAG-и

### `ingest_internal_sales_daily`
- Источник: CSV/XLSX upload или `data/inbox/`.
- Шаги:
  - обнаружение нового файла;
  - схема и типовая валидация;
  - запись в `import_jobs`;
  - загрузка в `sales_daily`.

### `ingest_internal_purchases_daily`
- Аналогичный пайплайн для закупок с загрузкой в `purchases_daily`.

### `ingest_external_indicators_daily`
- Источники: Rosstat, MOEX ISS, EIA при включении интеграций.
- В `v1` может быть реализован как stub или как один рабочий интеграционный пример.

### `build_feature_store_daily`
- Извлекает продажи, закупки и внешние индикаторы.
- Формирует лаги и календарные признаки.
- Сохраняет parquet-витрину для обучения и inference.

### `train_models_weekly`
- Запускает backtest.
- Сравнивает `CatBoost` с `Seasonal Naive`.
- Помечает лучшую модель `is_active=true`.
- Сохраняет артефакт модели и метрики.

### `news_digest_daily`
- Забирает новости по ключевым темам.
- Выполняет extractive summary либо LLM summary.
- Обновляет `news_raw`, `news_digests` и локальный RAG-индекс.

## Артефакты
- `artifacts/models/{product_code}/{horizon}/{version}/model.cbm`
- `artifacts/models/{product_code}/{horizon}/{version}/metrics.json`
- `artifacts/features/{run_date}/dataset.parquet`
- `artifacts/backtests/{product_code}/{horizon}/{run_id}.json`
- `artifacts/news/index/`

## Триггеры переобучения
- Плановый: раз в неделю через Airflow.
- Ручной: `POST /api/v1/backtests/run` администратором.
- Исследовательский `v2`: quality monitor с автоматическим сигналом о деградации.

## Acceptance criteria для ML-контура
- По каждому продукту существует baseline и основная модель.
- Для горизонтов `1/7/30` доступны метрики качества.
- Прогноз можно запросить вручную из UI.
- Система работает как с реальными импортами, так и с синтетикой.
- What-if сценарий учитывает изменение цены и явно помечает себя как сценарный режим.
