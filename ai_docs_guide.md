# Полное руководство по созданию документации для AI-разработки (Claude Code / Cursor / LLM-агенты)

> Этот файл — исчерпывающая инструкция для LLM-ассистента. Используй его как основу при создании любой проектной документации. Следуй описанным структурам, шаблонам и принципам.

---

## ЧАСТЬ 1. ФИЛОСОФИЯ И ПРИНЦИПЫ

### 1.1 Зачем нужна документация для AI-агентов

Документация для AI-проектов — это не артефакт «написал и забыл», а **исполняемая спецификация**. Качество сгенерированного кода напрямую зависит от качества входных данных, которые получает нейронка. Без документации:
- Каждый раз приходится заново объяснять контекст проекта
- Контекст чата разрастается, модель теряет фокус
- Нет единого источника правды — фичи конфликтуют друг с другом
- AI принимает произвольные решения вместо обоснованных

С документацией:
- Короткие промпты → точные результаты (модель берёт контекст из файлов)
- Консистентность между фичами и компонентами
- Возможность валидации — сверяем результат со спецификацией
- Экономия токенов — не дублируем информацию в каждом промпте

### 1.2 Spec-Driven Development (SDD)

Современный подход к AI-разработке. Три уровня зрелости:

1. **Spec-first** — спецификация пишется перед кодом и используется в AI-воркфлоу
2. **Spec-centric** — спецификация является основным поддерживаемым артефактом; код — производный
3. **Spec-as-code** — спецификация становится исполняемым чертежом

**Правило:** если можно написать unit-тест для валидации результата — масштаб задачи достаточно мал для простого промпта. Если нельзя — нужна спецификация.

### 1.3 Каскадный воркфлоу

Документация создаётся послойно, от общего к частному:

```
1. Идея проекта (project-idea.md)
   ↓
2. Маркетинг / ICP / Go-to-market (marketing/)
   ↓
3. Архитектура и тех. требования (frontend.md, backend.md)
   ↓
4. Описание фич (features/)
   ↓
5. Визуализация экранов (screens/)
   ↓
6. Промпты для AI-пайплайнов (prompts/)
   ↓
7. CLAUDE.md / .cursorrules — правила для агента
```

Каждый нижний слой ссылается на верхний. Нейронка читает сверху вниз и понимает контекст.

### 1.4 Принцип разделения файлов

- **Один файл = одна ответственность** (фича, экран, конфигурация)
- **Оптимальный размер файла: 100–400 строк.** Больше 500 — разбивать
- **Основной файл** содержит саммари + ссылки на подфайлы
- Нейронка открывает подфайл только когда ей реально нужна информация из него
- Это экономит контекстное окно и снижает вероятность «потери» инструкций

### 1.5 Принцип прогрессивной детализации

Не пытайся описать всё сразу. Документация растёт итеративно:

1. Написал базовое описание фичи
2. Попросил нейронку реализовать
3. Нейронка задала вопросы или сделала ошибку
4. Уточнил документацию в проблемном месте
5. Повторил

Каждая ошибка AI — сигнал дописать документацию.

### 2.2 Назначение каждой папки

| Папка | Что содержит | Когда создавать |
|-------|-------------|----------------|
| `docs/` корень | Идея проекта | Самое начало |
| `marketing/` | ICP, ЦА, боли, конкуренты, ценообразование | До начала разработки |
| `project/frontend/` | Стек, библиотеки, структура, конвенции фронтенда | Перед первой фичей |
| `project/backend/` | Стек, БД, API-структура, деплой бэкенда | Перед первой фичей |
| `features/` | Подробные спецификации каждой фичи | Перед реализацией фичи |
| `screens/` | ASCII-визуализации всех экранов | Параллельно с фичами |
| `prompts/` | Промпты для AI-пайплайнов внутри сервиса | При проектировании AI-логики |
| `adr/` | Записи об архитектурных решениях | При принятии ключевых решений |

## ЧАСТЬ 4. CLAUDE.md — ПРАВИЛА ДЛЯ CLAUDE CODE

### 4.1 Структура CLAUDE.md

CLAUDE.md автоматически загружается в начало КАЖДОЙ сессии Claude Code. Это самая важная точка конфигурации. Оптимальный объём: **50–150 строк** (максимум 300). Каждая строка потребляет контекст.

```markdown
# Project: [Название]

## About
[1-2 предложения о проекте]

## Architecture
- Frontend: [стек] в `/frontend`
- Backend: [стек] в `/backend`
- Database: [тип]

## Key Files
- Документация проекта: docs/
- Спецификации фич: docs/features/
- ASCII-экраны: docs/screens/

## Commands
- Frontend dev: `cd frontend && npm run dev`
- Backend dev: `cd backend && python manage.py runserver 8061`
- Frontend tests: `cd frontend && npm test`
- Backend tests: `cd backend && python manage.py test`
- Lint: `npm run lint` / `flake8`

## Code Style
- TypeScript: strict mode, named exports
- Python: PEP 8, type hints, 100 char line limit
- Components: один файл = один компонент, PascalCase
- API: RESTful, /api/v1/ prefix, JSON responses

## Important Rules
- ВСЕГДА читай релевантную спецификацию из docs/features/ ПЕРЕД реализацией фичи
- ВСЕГДА читай ASCII-экран из docs/screens/ ПЕРЕД созданием UI
- Следуй существующим паттернам в коде
- НЕ модифицируй файлы в docs/ без явного запроса
- НЕ создавай абстракции «на будущее» — минимум для текущей задачи
- Запускай тесты после каждого изменения
- Коммить после каждой завершённой фичи

## Conventions
- Git: conventional commits (feat:, fix:, docs:, refactor:)
- Branches: feature/[name], fix/[name], hotfix/[name]
- API responses: { data: ..., error: ..., meta: ... }

## Detailed Docs
- Frontend: @docs/project/frontend/frontend-docs.md
- Backend: @docs/project/backend/backend-docs.md
- Design System Format: @docs/project/design-system-format/README.md
```

### 4.2 Иерархия файлов памяти Claude Code

| Приоритет | Файл | Где живёт | Назначение |
|-----------|-------|----------|------------|
| 1 (высший) | Enterprise CLAUDE.md | `/Library/Application Support/ClaudeCode/` | Политики организации |
| 2 | Project CLAUDE.md | `./CLAUDE.md` | Правила проекта (в git) |
| 3 | Project local | `./CLAUDE.local.md` | Личные настройки (gitignored) |
| 4 | User memory | `~/.claude/CLAUDE.md` | Глобальные личные предпочтения |
| 5 | Auto memory | `~/.claude/projects/[hash]/MEMORY.md` | Авто-заметки Claude |

Дочерние `CLAUDE.md` в поддиректориях загружаются по требованию — только когда Claude работает в этой директории.

### 4.3 Что НЕ надо включать в CLAUDE.md

- Подробные примеры кода (выноси в отдельные файлы)
- Конфигурации TypeScript/ESLint/Prettier (они в своих конфигах)
- Полные API-контракты (они в docs/features/)
- Туториалы и обучающие материалы
- Информацию, которая не влияет на поведение агента

**Тест: «Если убрать эту строку, будет ли Claude делать ошибки?» Если нет — удалить.**

## ЧАСТЬ 5. CURSOR RULES

### 5.1 Формат .mdc файлов

Файлы в `.cursor/rules/*.mdc`. Каждый файл — YAML frontmatter + Markdown:

```yaml
---
description: "React component patterns for this project"
globs: "src/components/**/*.tsx"
alwaysApply: false
---

# React Component Standards
- Функциональные компоненты с arrow function
- TypeScript interface для пропсов: `{Name}Props`
- CSS: только Tailwind utility classes
- Один компонент = один файл
- Не используй default exports
```

### 5.2 Режимы активации

| Режим | Настройка | Когда срабатывает |
|-------|----------|------------------|
| Always Apply | `alwaysApply: true` | Каждая сессия |
| Auto Attached | `globs: "*.tsx"` | При работе с файлами по паттерну |
| Agent Requested | `description` заполнено | AI решает по описанию |
| Manual | Все поля пустые | Только при `@rule-name` |

### 5.3 Рекомендации

- Один файл правил < 500 строк
- `description` — самое важное поле (по нему AI решает, применять ли правило)
- Используй `@filename.ts` ссылки вместо копирования кода
- Готовые правила: cursor.directory, github.com/PatrickJS/awesome-cursorrules

## ЧАСТЬ 6. ОПТИМИЗАЦИЯ КОНТЕКСТА

### 6.1 Контекстное окно Claude Code

- Размер: ~200K токенов
- Базовый расход (системный промпт + CLAUDE.md): ~20-30K
- Автокомпрессия при ~83.5% заполнения
- **Качество заметно падает после 75% заполнения**

### 6.2 Практики экономии контекста

1. **`/clear` между несвязанными задачами** — полный сброс. История отладки бесполезна при реализации нового эндпоинта
2. **`/compact` при 70-75%** — не жди автокомпрессию. Можно с фокусом: `/compact Focus on API changes`
3. **Субагенты для исследований** — работают в отдельном контексте, возвращают только саммари
4. **Планы в внешних файлах** — `PLAN.md`, `TODO.md`. При неудаче: `/clear` + перезагрузка плана
5. **Lean CLAUDE.md** — каждая лишняя строка расходует контекст в КАЖДОЙ сессии
6. **Разбивай документацию на файлы** — Claude открывает только нужные
7. **Комбинируй инструменты** — Cursor для генерации документации (дешевле), Claude Code для валидации и реализации
8. **Новый чат для каждой отдельной задачи** — не тащи контекст предыдущих задач

### 6.3 Plan Mode

Shift+Tab в Claude Code. Агент читает и исследует, но НЕ модифицирует файлы.

Рекомендуемый поток:
1. Plan Mode → анализ → запись плана в PLAN.md
2. Normal Mode → «Реализуй план из docs/PLAN.md шаг за шагом»
3. Коммит после каждого шага
4. При неудаче: `/clear` → перезагрузка PLAN.md → продолжение

```
│   └── Попросить нейронку предложить конфигурацию

└── Разбить большие файлы (>500 строк) на подфайлы

Шаг 4: Фичи (2-4 часа)
├── Составить список всех фич проекта
├── Для каждой фичи написать docs/features/[name].md
│   ├── Написать базовые требования самому
│   ├── Попросить нейронку дополнить (plan mode)
│   ├── Проверить и скорректировать

Шаг 5: Экраны (1-2 часа)
├── Для каждого уникального экрана создать docs/screens/screen-[name].md
├── Нарисовать ASCII-визуализацию

Шаг 6: CLAUDE.md (30 мин)

├── Включить: about, architecture, commands, code style, rules

└── Проверить объём: < 150 строк

Шаг 7: Начать разработку
├── Короткие промпты: «Реализуй фичу X согласно docs/features/X.md»
├── Коммит после каждой фичи

└── Повторять
```

### 8.2 Работа с нейронкой при создании документации

**Для генерации документации используй чат (Cursor / Claude.ai), не Claude Code:**
- Claude Code сжигает лимиты быстрее
- Для документации не нужны инструменты файловой системы
- Cursor позволяет использовать plan mode для планирования

**Рабочий цикл в чате:**
1. Переключись в Plan Mode
2. Дай нейронке контекст (прикрепи project-idea.md + маркетинг)
3. Опиши свои требования к фиче
4. Нейронка задаёт уточняющие вопросы — ответь на все
5. Нейронка генерирует план — проверь и одобри
6. Нейронка создаёт файлы — проверь каждый
7. Скорректируй то, что не нравится
8. Коммит

**Для валидации документации используй Claude Code:**
1. Попроси проанализировать всю документацию на:
   - Несоответствия (порты, версии, названия)
   - Избыточные зависимости
   - Корректность конфигураций (через Context7 MCP)
2. Примени рекомендованные исправления
3. Коммит

### 8.3 Когда документация готова

Документация считается достаточной для начала разработки, когда:
- [ ] Есть описание идеи и ЦА
- [ ] Описан стек фронтенда и бэкенда
- [ ] Каждая фича имеет свой файл с user flow, API-контрактами и состояниями
- [ ] Есть ASCII-экран для каждого уникального UI
- [ ] CLAUDE.md создан и ссылается на ключевые файлы
- [ ] Нет конфликтов (порты, названия, версии)

**Документацию НЕ нужно делать идеальной.** Она дорабатывается в процессе разработки. 80% качества достаточно для старта.
